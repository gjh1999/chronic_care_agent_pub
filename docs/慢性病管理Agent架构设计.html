01 设计原则与决策

决策结论理由
语言Python（FastAPI）核心资产（LangGraph / 规则引擎 / RAG）全在 Python 生态；公司答题系统已验证 FastAPI 工程化生产可行；本系统瓶颈在 LLM 等 I/O，不在 CPU 计算
工作流编排保留 LangGraph多意图解析 + 条件路由 + 人机协同是本项目核心价值，重写等于降级
工程规范对齐答题系统分层 controller→service→dao→entity、统一响应、软删、JWT+Redis、两层配置，全部照搬成熟规范
数据库PostgreSQL 16 + alembic业务 UUID + 精简审计/版本字段 + 软删；只有公司规范强制时才扩展同步元数据；单元测试可切 SQLite
前端uni-app → 微信小程序患者端触达成本低；本地与受控体验测试使用虚构或脱敏数据，真实用户测试另行完成数据与合规评估
医生端本版不做，预留数据层预留 doctor / doctor_patient 绑定；前端医生端倾向网页形态，后续按同一接口契约扩展
改造基调「外围工程化 + 核心保留」：LangGraph 图、节点、规则引擎、RAG、用户画像全部复用；改造集中在 API 层规范、数据库、鉴权、配置、工程脚本。改造完成后，未来若需 Java 化，只需按本文档的表设计与接口契约翻译，不重设计。

03 后端分层规范 对齐答题系统

  • controller（app/controller/v1/{chat,health,plan,reminder,user,sys}/）只做参数接收与 ResponseUtil.success(...)；路由统一 APIRouter(prefix='/api/v1/...', dependencies=[Depends(LoginService.get_current_user)])，管理员端点再加 Depends(CheckRoleInterfaceAuth('admin'))。
  • service（app/service/v1/...）是业务实现所在：health_service（记录写入，REST 与工作流 record_node 共用）、plan_service、reminder_service、login_service（JWT + Redis 会话）、sys_param_service（运行参数）、user_service。工作流节点（nodes）是编排语境下的业务单元，内部调用 service / dao，不在节点里直接写 SQL 或裸调 DB。
  • dao（app/dao/v1/）数据访问：HealthRecordDao / PlanDao / ReminderDao / SysUserDao / SysParamDao，只做装载与查询组装。
  • entity：do 一表一文件、继承 BaseDO（默认 6 个审计/版本字段，可按公司强制规范扩展）；vo 是 Pydantic 视图模型。
  • 统一响应 {code, data, message, request_id}，code=0 成功；HTTP 状态保留标准语义，body code 表达细分业务原因。抛 ServiceException(message, error_code, http_status)，全局处理器在 app/exceptions/handle.py。
  • 软删过滤器（app/config/orm_event.py）：所有 SELECT 自动加 deleted_at IS NULL；需要查询已删行时显式加 .execution_options(include_deleted=True)。
  • 工作流与分层的关系：消息接口与 interrupt resume 接口是进入 LangGraph 的入口；REST 数据接口走 controller→service→dao，不经过图。两条路径共用同一套 service 业务实现，避免逻辑分叉。

保留不变的规则（红线）

  • 计划必须用户确认后才生效（confirm / reject / modify 三态）
  • Reminder 只能基于 confirmed_plan 创建
  • 新计划必须过冲突检测，冲突计划不能直接覆盖旧计划
  • 高风险数据：规则引擎拦截，建议生成走保守路径
  • LLM 只负责认知（理解 / 生成），Rule 负责安全

本版适配点

  • user_id 来源：前端传 → JWT 解析（防越权）
  • 节点写库：直接调 crud → 调 service（与 REST 共用实现）
  • User Confirm 节点：LangGraph interrupt() 暂停并持久化状态；客户端使用独立确认接口携带 interrupt_id + action + revision 恢复
  • Response Node 输出结构对齐 {code,data,message}

4.1 会话、中断与恢复协议

  1. 新消息创建或复用 conversation_id，该值同时作为 LangGraph thread_id；用户身份只取自 JWT。
  2. 计划草稿生成后保存 care_plan(status=draft, revision=N)，工作流调用 interrupt()，响应返回 status=waiting_confirmation、interrupt_id、计划摘要和 revision。
  3. 客户端调用确认接口提交 confirm / reject / modify。服务端校验 conversation 所有权、interrupt_id、revision 和幂等键，再通过 Command(resume=...) 恢复。
  4. 同一个 interrupt 只能成功处理一次；重复提交返回首次处理结果。revision 不一致返回 409/40005，避免旧页面覆盖新计划。
  5. 服务重启后必须能从 PostgreSQL checkpointer 恢复；不得依赖 Python 进程内存保存等待状态。
确认机制现状（2026-10-24）user_confirm_node 只保留调用方传入的 user_confirmed 状态、禁止默认同意；确认恢复由 conversation_checkpoint 表 + resume_interrupt 实现（interrupt_id / revision 乐观锁 / 幂等），confirm 时由 plan_service.confirm_plan 生效计划并创建计划提醒。详见子页面第 07 节。

05 数据库设计

5.1 表规范（全部业务表统一）

  • 对外业务标识统一使用 PostgreSQL 原生 UUID。若公司基础框架强制要求，可保留自增内部主键 + 业务 UUID；否则直接以 UUID 为主键，避免双标识增加复杂度。
  • 通用元数据默认使用 created_at / created_by / updated_at / updated_by / deleted_at / version。org_code / is_upload / upload_time / is_force 仅在存在组织隔离或离线同步需求时启用，不机械照搬。
  • 表间引用一律使用业务 UUID；父行先 flush() 再创建子行。所有状态变更使用 version 做乐观锁。
  • 来自请求的 UUID 先 is_uuid() 校验，不合法当不存在；create_by / update_by 只能是用户 uuid 或 NULL。
  • 时间列 timestamp，VO 由 BaseVO 统一格式化成 YYYY-MM-DD HH:MM:SS。
  • 结构由 alembic 管理：改 DO → alembic revision --autogenerate -m "xxx" → alembic upgrade head。
  • 软删使用 deleted_at；SELECT 默认过滤。审计、恢复场景通过显式 execution option 查询已删数据。
  • 健康数据写入支持 Idempotency-Key 或 source_event_id 唯一约束，防止网络重试和设备同步产生重复记录。

06 鉴权体系 JWT + Redis 会话

登录链路（小程序）

  1. 小程序 wx.login() 拿临时 code → POST /api/v1/login {code}
  2. 后端调微信 code2session 换 openid
  3. openid 查 sys_user：不存在则注册（首次登录建号），存在则继续
  4. 签发标准 JWT（HS256，payload 只有 sub / session_id / iat / exp），同时写 Redis access_token:{session_id}
  5. 每次登录新 session_id，多端互不影响

请求校验

  • 每个请求 Authorization: Bearer <令牌>，LoginService.get_current_user 校验签名（只认配置里的算法，防 alg=none）、查 Redis 会话并续期、角色现查数据库（停用账号拿旧令牌也无效）
  • 登出删除 Redis 会话后即刻失效；生产环境 Redis 不可用时拒绝登录或返回服务不可用，不降低为不可撤销的纯 JWT
  • 本期角色为 admin（管理员）和 patient（患者）；权限判断使用策略/依赖，不把“永远只有两类角色”写死，为后续独立医生权限模型预留空间
  • 所有涉及 user_id 的资源操作（记录 / 计划 / 提醒）强制以 JWT 里的身份为准，杜绝传参越权
  • 登录、对话、记录写入和确认接口按用户与 IP 限流；连续失败和异常访问写入 audit_log

参数 ★ /sys/paramGET list · PUT upsert · DELETE {param_id}
接口拆分动机现状只有 POST /api/chat 一个接口，小程序的历史记录页、计划页、趋势图都必须走 REST 直查，不能每次都跑一遍图。工作流只负责「对话式交互」，数据型页面走标准 CRUD。

8.1 通用接口契约

  • 成功响应统一为 {code:0,data,message,request_id}；HTTP 状态保持标准语义：400 参数错误、401 未认证、403 无权限、404 不存在、409 状态/版本冲突、429 限流、503 依赖不可用。
  • 列表统一使用 page_no/page_size，响应 {items,total,page_no,page_size}；时间使用带时区的 ISO 8601，数据库统一存 UTC。
  • 资源接口永远不接收可覆盖当前身份的 user_id；管理员代查使用独立、审计化的管理端接口。
  • 所有写接口支持 request-id；健康记录、确认和提醒创建必须支持幂等，防止小程序重试造成重复副作用。

11 部署、运行与数据安全

阶段形态说明
本地开发uvicorn :8000 + SQLite/PG只使用虚构或脱敏数据；微信开发者工具可在开发设置下连接本机或局域网后端
受控体验测试体验版 + 测试环境 PG/Redis限定测试成员、独立测试数据、HTTPS、访问日志脱敏；不因“体验版”而跳过个人信息和健康数据保护
生产发布PG + Redis + API + worker + nginx上线前由业务与法务确认主体、类目、备案、隐私政策、第三方模型处理、数据存储地域和医疗安全边界；结论不在技术文档中预设

11.1 生产基线

  • API 与 worker 分进程部署；Docker 启动命令先执行 alembic upgrade head，迁移失败则停止发布。
  • 提供 /healthz（进程存活）和 /readyz（PG/Redis/关键配置就绪）；nginx 只把 ready 实例加入流量。
  • 日志包含 request_id、user_id 哈希、接口、耗时和错误类别；禁止记录 token、openid、完整健康数据、完整提示词和模型密钥。
  • PostgreSQL 自动备份并定期做恢复演练；迁移有回滚/前向修复方案。提醒 worker 使用数据库锁或 skip-locked，确保多实例下不重复投递。
  • 监控 API 错误率、LLM/RAG 超时与 token、规则高风险命中、提醒积压与发送失败；设置告警阈值。
数据边界本地技术验证可不连接真实业务系统，但只要使用真实用户健康数据、把数据发送给第三方模型或邀请外部用户使用，就必须先完成相应的数据处理、授权与安全评估，不能以“开发/体验环境”为由自动豁免。

11.2 医疗安全与模型边界

  • 产品定位为健康记录、生活方式建议和提醒工具，不输出诊断结论，不生成或调整处方，不替代医生。
  • 血压、血糖及危险症状先经过确定性规则；达到高风险阈值时直接输出固定升级提示，禁止由 LLM 弱化、覆盖或延迟。
  • LLM 输出必须通过 Pydantic/JSON Schema、单位与数值范围、计划禁忌和引用证据校验；失败时返回安全降级文案，不把原始模型文本直接展示。
  • RAG 文档记录来源、版本、生效日期和适用人群；答案展示证据摘要。检索内容视为不可信输入，不能覆盖系统安全规则或索取秘密。
  • 对提示词注入、越权工具调用、异常超长输入、重复请求和模型超时建立测试；所有关键决策记录规则版本和模型版本以便追溯。
