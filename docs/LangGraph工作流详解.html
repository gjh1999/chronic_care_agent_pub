01 工作流总览

整个工作流是一个 StateGraph(ClinicalState) 主图,内部挂载一个 plan_reminder_sub 子图。入口统一为 run_workflow(user_input, user_id, conversation_id, user_confirmed):

Memory 注入memory_service.load_user_memory画像 + 任务偏好进入初始状态
图执行_graph.invoke(initial_state)parser → … → response
Memory 更新update_from_session_summary从 advice + final_response 提取长期偏好
HTTP 入口POST /conversations/{id}/messages · JWT 解析 user_id → run_workflow
↓
外部意图服务解析parser_node → Medical_Lora(8020)· Qwen2.5-7B routing LoRA
↓
normalize 归一化补全依赖:need_plan→need_advice→history+risk+rag
↓
route_after_normalize: need_record → 记录 | need_advice → 分析链 | plan/reminder → 子图
↓
plan_reminder_sub 子图计划链(draft→conflict→confirm→archive)与直接提醒链,详见 04 节
↓
response 汇总输出拼装 final_response(🚨/✅/💡/📋/⏰)
↓
END结果返回 conversation_service 落消息、判 waiting_confirmation
双层编排主图负责「意图解析 → 记录 → 健康分析(历史/风险/RAG/建议)→ 计划与提醒 → 输出」的主干;子图负责计划的两阶段确认与直接提醒两条业务链。子图在主图中只是一个普通节点(NODE_PLAN_REMINDER_SUB = "plan_reminder_sub"),结束后固定回到 response 节点。

03 意图归一化 app/graph/normalizer.py

parser 输出的 intent.routing 直接成为 intent_flags,normalize 节点在此基础上补全依赖关系,保证后续路由不出现"想给建议却没有查历史"这类断链:

规则说明
need_plan → need_advice = True计划必须基于建议(分析链先行)
need_advice → need_history + need_risk + need_rag = True建议需要历史、风险与证据三件套
reminder_sourceneed_reminder 且 need_plan → "plan";仅 need_reminder → "direct"。当前仅作信息用途(计划提醒改由确认服务创建,见 08 节)
行为观察(2026-10-24 E2E)意图模型对「血压145/92,这正常吗?」这类纯提问会额外输出 need_record=true(提及测量值即隐含记录),主项目会因此落一条观测。若产品不想要隐式记录,需在意图服务侧调整训练样本或加后处理。

07 人机协同协议 两阶段确认 · conversation_service

计划采用「草稿 → 用户确认 → 生效」两阶段,确认状态由 conversation_checkpoint 表管理(项目自研协议,不依赖 LangGraph interrupt()/Command):

① 首轮消息run_workflow(user_confirmed=None)子图停在确认路由,plan_draft 返回
② 存草稿create_draft(status=draft, revision=1)+ checkpoint(waiting) + 会话转 waiting_confirmation
③ 响应interrupt_id + revision + plan客户端展示计划卡片
④ 恢复resume_interrupt(action, revision)校验 checkpoint → 执行业务
⑤ 完成status=completed · 会话转 activeaudit_log 记录 plan.{action}

7.1 resume 校验链(按顺序)

  1. 会话存在且属于当前用户(JWT 身份);
  2. interrupt_id 存在;revision 一致,否则 409「计划版本已变化,请刷新后重试」;
  3. checkpoint 未被处理过 —— 已处理且同 action 直接返回首次结果(幂等);
  4. 未过期(expires_at,默认 7 天),过期返回 409。

7.2 三种动作

action行为
confirmplan_service.confirm_plan:状态 draft → confirmed(revision+1),并按计划项创建提醒(见 08 节)
rejectchange_plan_status(..., "reject"):状态 draft → rejected
modifyreject 旧计划 + 以「请根据以下要求修改刚才的计划:…」重新 send_message 跑一轮工作流(新草稿、新 checkpoint)
幂等保障checkpoint 状态机 waiting → resumed 保证同一 interrupt 只成功处理一次;重复提交返回首次结果。计划状态变更以 revision 做乐观锁。

08 提醒机制 直接提醒 + 计划提醒 + outbox + worker

8.1 两条创建路径

直接提醒(对话)

「明早8点提醒我测血糖」→ direct_reminder_node 取 slots → reminder_create_node → create_reminder。

dedupe_key = reminder:{id}:{uuid},无幂等键冲突风险。

计划提醒(确认时)

计划确认(API resume 或工作流 archive)→ confirm_plan 逐计划项创建提醒,plan_item_id 关联回 care_plan_item。

dedupe_key = plan:{plan_id}:{item_id},重复确认不重复创建。无时间/解析失败的计划项进入 skipped 返回,不静默丢失。

8.2 时间解析(2026-10-24 修复 F3)

  • resolve_next_run_at(schedule_rule):支持自然语言(明早8点/明晚9点/晚上9点/下午3点半)、HH:MM、显式 YYYY-MM-DD;统一换算为 aware UTC(中国固定 +8);
  • 解析出的时刻已过去(如 22 点解析 "21:00")自动顺延到次日同一时刻;
  • 解析失败 → create_reminder 抛 422「提醒时间无法解析」,禁止静默按"立即"投递。

8.3 可靠投递(outbox + worker)

写提醒reminder(next_run_at, scheduled)与 outbox 同事务
写 outboxavailable_at = next_run_atdedupe_key 唯一
worker 轮询available_at ≤ now · status=pending锁定逐条投递
结果回写sent / failed · attempts +1指数退避,最多 5 次
未覆盖worker 的真实投递链路(in_app 通道实现/微信模板)尚未在线验证;当前 deliver_wechat 未配置。数据库侧 available_at 语义已修复(E2E 隔离库核查:立即投递行数为 0)。

11 安全保障 规则兜底 · 确认机制 · 可追溯

规则先于 LLM

  • 血压 ≥180/120 或血糖高危 → level=urgent,本地固定文案拦截,不经过 RAG/LLM,计划与提醒全部跳过
  • LLM 只负责认知(理解/生成),Rule 负责安全

证据门控

  • RAG 证据必须质量通过(suggested_action ∈ {continue, retry_done} + quality_passed)才喂给 LLM
  • 需人工确认 / 需澄清 / 证据不足 / 服务不可用 → 固定安全文案,不生成医学结论

人机协同

  • 计划必须用户确认才生效;user_confirm 节点禁止默认同意
  • checkpoint 幂等 + revision 乐观锁,旧页面无法覆盖新计划

副作用可靠

  • 提醒时间解析失败 → 422 明确报错,禁止静默立即投递
  • 提醒 + outbox 同事务写入,dedupe_key 幂等,worker 可重试
  • 健康记录支持 source_event_id 幂等约束
